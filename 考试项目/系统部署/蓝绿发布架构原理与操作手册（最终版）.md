# 蓝绿发布架构原理与操作手册（最终版）

本手册详述了当前系统的蓝绿部署架构核心运行原理、完整配置文件以及标准发版操作流程，旨在指导运维与开发人员实现系统的**零停机、无感知**平滑升级。

## 第一部分：架构原理解析

当前的蓝绿发布机制巧妙地利用了 **Nginx 的被动健康检查与重试机制**、**Docker 容器独立环境**以及 **Spring Boot 的优雅停机**，构成了一套轻量级的高可用发布方案。

### 1. 流量调度与无感切流 (Nginx 侧)

- **双节点全时代理**：在 `nginx.conf` 中，`upstream backend_servers` 同时配置了 Blue (16290) 和 Green (16291) 两个节点。
- **被动健康探测 (`max_fails`** **&** **`fail_timeout`)**：如果某个节点在 5 秒内连续出现 2 次异常（如连接拒绝、502 等），Nginx 会自动将其临时“拉黑” 5 秒，不再分发流量。
- **请求自动重试 (`proxy_next_upstream`)**：这是**实现无感知的核心**。当用户的请求被打到正在关机的旧节点，导致超时或 502/503/504 时，Nginx 会截获这个错误，并在后台默默将**原请求原封不动地转发给存活的新节点**。前端用户完全不会感知到报错。

### 2. 进程安全退出 (Spring Boot & Docker 侧)

- **Spring Boot 优雅停机**：`spt.env` 中配置了 `SERVER_SHUTDOWN=graceful`。当应用收到停机信号时，它会立刻拒绝**新的请求**，但会继续处理**正在执行的请求**（如大文件上传），最长等待时间设定为 10 分钟。
- **Docker 停机宽限期**：`docker-compose.yaml` 中配置了 `stop_grace_period: 10m`。这保证了在使用 `docker-compose stop` 时，Docker 会先发送 `SIGTERM` 信号给 Java 进程，并安全等待最多 10 分钟。如果 10 分钟后进程仍未退出，才会发送强制杀死的 `SIGKILL` 信号，完美配合 Spring Boot 的优雅停机。

### 3. 资源隔离与按需拉起

- **日志隔离**：Blue 和 Green 分别挂载了不同的日志子目录（`spt/logs/spt-blue` 和 `spt/logs/spt-green`），避免日志文件冲突和相互覆盖。
- **默认配置 (`profiles: ["donotstart"]`)**：Green 服务配置了该属性，这意味着在使用 `docker-compose up -d` 启动全局基础架构时，只会默认启动 Blue 服务，以节省平时运行的服务器资源。

### 2. `nginx_gateway/nginx.conf`

Nginx

```
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    include       mime.types;
    default_type  application/octet-stream;

    sendfile        on;
    keepalive_timeout  65;

    # =================================================================
    # 1. 蓝绿动态上游（全 host 模式下直接走本地回环）
    # =================================================================
    upstream backend_servers {
        # max_fails=2 fail_timeout=5s: 5秒内如果连续撞到2次503或错误，Nginx 会自动临时拉黑该节点 5 秒
        server 127.0.0.1:16290 max_fails=2 fail_timeout=5s; # 蓝色服务 (spt-blue)
        server 127.0.0.1:16291 max_fails=2 fail_timeout=5s; # 绿色服务 (spt-green)
    }

    server {
        listen       16390;
        server_name  localhost;

        # =================================================================
        # 3. 动态 API 反向代理与平滑切流
        # =================================================================
        location / {

            proxy_pass http://backend_servers;

            # 透传真实客户端 IP 与 Host 头部
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

            # 核心容错：后端若是 502/503/504 或超时，Nginx 默默转给另一个节点，用户完全无感
            proxy_next_upstream error timeout invalid_header http_502 http_503 http_504;
            proxy_next_upstream_tries 2;
            proxy_next_upstream_timeout 5s;
        }
    }
} 
```

## 第三部分：蓝绿发布操作手册

> **💡 核心构建理念（不可变基础设施）：** 系统的 Jar 包是通过 `COPY` 指令固化进镜像内部的。每次发布最新编译的 Jar 包后，**必须使用** **`--build`** **参数**指示 `docker-compose` 重新构建镜像层，否则容器只会继续拉起历史旧镜像。

系统默认常态下仅单独运行 `spt-blue` 服务，发版时通过蓝绿双服务轮流交替（“跷跷板”模式）实现平滑升级。

### 场景一：当前运行的是 Blue，发布新版本到 Green

**步骤 1：替换最新构建包** 将最新编译的 `spt-boot.jar` 上传至服务器，覆盖宿主机目录下的 `./spt/spt-boot.jar`。

**步骤 2：构建并拉起 Green 服务（一步到位）** 执行以下命令，系统会读取最新的 Jar 包并强制重新构建 `spt-green` 镜像，随后在后台将其拉起：

Bash

```
docker-compose up -d --build spt-green 
```

_(注：显式指定服务名_ _`spt-green`_ _会无视 yaml 中的 profiles 限制将其强制拉起)_

**步骤 3：观察 Green 服务启动日志** 持续跟进日志流，确保新版本服务已完全成功初始化：

Bash

```
docker-compose logs -f spt-green 
```

_当日志输出_ _`Started Application in X seconds`_ _成功标志后，表明 16291 端口已就绪。此时 Nginx 会自动开始将一半的动态流量分发给 Green 服务。_

**步骤 4：功能验证（推荐）** 抽样请求核心系统接口或刷新业务前端页面，验证新版本功能无基本面异常。

**步骤 5：优雅下线旧的 Blue 服务** 确认 Green 运行无误后，安全停止旧的 Blue 服务：

Bash

```
docker-compose stop spt-blue 
```

_此时，Docker 会向 Blue 容器投递_ _`SIGTERM`_ _信号。Blue 服务会拒绝新请求，并安全处理完当前已承接的老请求。Nginx 探测到 Blue 端口关闭后，会自动重试并把后续所有业务流量 100% 切换给 Green。发版顺利完成。_

### 场景二：当前运行的是 Green，发布新版本到 Blue (下一次发版)

当进入下一个迭代发版周期时，执行反向的交替操作。

**步骤 1：替换最新构建包** 将最新编译的 `spt-boot.jar` 覆盖宿主机 `./spt/spt-boot.jar`。

**步骤 2：构建并拉起 Blue 服务**

Bash

```
docker-compose up -d --build spt-blue 
```

**步骤 3：观察 Blue 服务启动日志**

Bash

```
docker-compose logs -f spt-blue 
```

_等待_ _`Started Application`_ _日志标志。_

**步骤 4：优雅下线旧的 Green 服务** 确认 Blue 服务启动成功且验证无误后，停止旧的 Green 服务：

Bash

```
docker-compose stop spt-green 
```

## 第四部分：应急预案与回滚操作

如果在启动新服务并切入流量后（步骤 3 和步骤 4 之间或之后），发现新版本存在突发严重缺陷（如大面积报错、逻辑死锁等），执行以下步骤进行**秒级快速回滚**：

1. **立刻重新唤醒旧版本服务**： 假设当前刚上线的 Green 出现故障，Blue 刚被停掉。立刻重新拉起处于存量镜像状态的 Blue 服务：

   Bash
   ```
   docker-compose start spt-blue 
   ```
   _因为 Blue 镜像是上一版本的历史镜像，此命令可以瞬间让老版本复活并接管流量。_
2. **强制下线有问题的故障服务**： 确认旧服务（Blue）重新正常接管流量后，立刻停掉新服务（Green）：

   Bash
   ```
   docker-compose stop spt-green 
   ```
   _(若情况极其恶劣、需要紧急阻断，可直接执行_ _`docker-compose kill spt-green`_ _强制掐断其进程以消弥影响)_。
