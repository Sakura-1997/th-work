客户端新版本检测与一键更新功能技术方案
（泰豪科技AI数字化平台二期升级项目配套方案）
一、需求概述
1.1 需求描述
客户端启动及运行期间自动检测服务端是否有新版本发布。当检测到新版本时，在客户端主界面左下角显示一个下载按钮（如图1样式：蓝色圆形图标按钮，内嵌白色下载箭头图标），用户点击该按钮后立即开始下载更新包；下载完成后提示用户安装并重启客户端，完成版本升级。
该机制替代传统的"弹窗强制提示、跳转网页手动下载"方式，将更新入口常驻于界面左下角，不打断用户当前操作，实现"发现新版本—一键下载—安装更新"的闭环。
1.2 建设目标
无感检测：客户端自动完成版本检查，用户无需任何操作即可获知新版本；
轻量提示：仅在左下角显示图标按钮，不弹窗、不中断业务操作；
一键更新：点击按钮即开始下载，全程显示进度，下载完成引导安装；
安全可控：更新包经哈希与签名校验，下载支持断点续传与失败重试；
灰度发布：支持按租户、按用户比例分批推送新版本，降低发布风险。
1.3 与平台整体方案的关系
本方案为平台二期实施方案中"服务广场门户/客户端"的配套能力。版本检查与更新包下载接口复用平台统一网关与统一身份认证体系；更新包存储复用平台对象存储/文件服务；客户端前端沿用二期主流Web前端框架（桌面客户端为Web前端的桌面壳形态），不引入新的技术栈。
二、总体方案
2.1 方案架构
功能由三部分组成：版本检查服务（服务端）、更新包分发（存储与下载）、客户端更新模块（检测、提示、下载、安装）。整体交互流程如下：
客户端启动时及运行中定时（默认每4小时）向版本检查服务发起版本查询请求，携带当前版本号、客户端类型（Windows/macOS/Web）、租户与用户标识；
版本检查服务比对最新发布版本与灰度规则，返回"是否有新版本"及更新元数据（版本号、更新说明、下载地址、文件大小、SHA-256哈希、是否强制更新）；
客户端检测到新版本后，在主界面左下角渲染下载按钮（图1样式）；
用户点击按钮，客户端通过HTTPS下载更新包至本地临时目录，按钮切换为进度态（环形进度条）；
下载完成后客户端校验SHA-256哈希与数字签名，按钮切换为"安装"态；
用户确认后执行安装：桌面客户端退出并启动安装程序（或自动替换应用文件后重启）；Web端客户端则刷新并清理缓存加载新版本静态资源。
2.2 版本检查服务
在平台后端新增轻量的版本管理服务（建议随门户后端建设），负责：
版本元数据管理：维护各客户端类型的发布版本、更新说明、更新包地址、哈希值、签名、发布状态（草稿/灰度/全量/下线）；
灰度规则引擎：按租户白名单、用户ID哈希百分比（如5%→30%→100%）控制新版本可见范围；
强制更新策略：对存在重大安全修复的版本标记强制更新，旧版本客户端启动时阻断使用并引导更新；
更新统计：记录检查次数、下载量、升级成功/失败率，纳入运营管理层统计视图。

3.3 交互细节
检测时机：客户端启动完成后立即检查一次；此后每4小时轮询一次；Web端同时监听服务端SSE通道，新版本发布时实时收到通知，无需等待轮询；
不打扰原则：检测与提示全程无弹窗（强制更新除外）；按钮常驻左下角直到用户完成更新或新版本被服务端下线；
下载过程：下载在后台线程进行，不影响客户端正常使用；网络中断自动重试3次，支持Range断点续传；
安装确认：安装前弹出一次确认框（展示版本号与更新说明），确认后客户端保存当前会话状态再重启，避免数据丢失。
四、接口设计
4.1 版本检查接口
客户端通过平台统一网关调用，请求头携带一期统一身份认证令牌，接口按透传的租户上下文匹配灰度规则。
GET /api/v1/client/version/check?currentVersion=2.1.0&amp;clientType=windows&amp;channel=stable
响应示例（检测到新版本）：
{
  "code": 0,
  "data": {
    "hasUpdate": true,
    "latestVersion": "2.2.0",
    "forceUpdate": false,
    "releaseNotes": "1. 新增...\n2. 修复...",
    "package": {
      "url": "https://&lt;内网域名&gt;/updates/app-2.2.0-win-x64.exe",
      "size": 89456320,
      "sha256": "a1b2c3...",
      "signature": "Base64(RSA-SHA256签名)"
    }
  }
}
字段说明：hasUpdate为false时客户端保持按钮隐藏；forceUpdate为true时客户端启动流程直接引导更新，不允许跳过。
4.2 更新包下载接口
更新包存放于平台对象存储/文件服务，经统一网关鉴权后下载（静态大文件可配置内网Nginx直接分发，网关只做鉴权跳转）。下载接口必须支持HTTP Range请求以实现断点续传，响应头携带Content-Length与Accept-Ranges: bytes。

五、客户端实现方案
5.1 桌面客户端（Windows/macOS）
若客户端为桌面壳形态（如Electron类架构），更新模块复用其成熟的自动更新机制（如electron-updater），本方案的版本检查服务输出兼容的更新元数据（latest.yml/latest.json格式）即可无缝对接；左下角按钮与状态机由前端按第3章规范自绘，通过IPC与主进程通信控制下载与安装：
检测：渲染进程定时调用版本检查接口，或主进程调用autoUpdater.checkForUpdates()；
下载：主进程执行下载并校验，通过IPC推送download-progress事件，渲染进程更新按钮进度；
安装：调用quitAndInstall()，安装前由渲染进程保存用户会话状态。
5.2 Web端客户端
纯Web形态下"更新"体现为前端静态资源与服务端版本的同步：
前端构建产物按版本号带哈希文件名发布，index.html不缓存；
版本检查接口返回最新前端资源版本号，检测到不一致时左下角显示下载按钮；
点击按钮后预加载新版本静态资源（Service Worker预缓存），完成后提示"点击刷新应用新版本"。
5.3 关键实现要点
版本比较：采用语义化版本（SemVer，主.次.修订）比较，杜绝字符串比较错误；
临时目录：更新包下载至系统临时目录下的专用子目录，按版本号命名，安装完成或失败后清理；
并发与幂等：按钮点击后置为下载中状态，防止重复触发；客户端重启后若检测到已下载且校验通过的更新包，直接进入待安装状态，不重复下载；
日志：检测、下载、校验、安装各环节写本地日志并上报服务端，用于失败排查与升级成功率统计。
六、安全设计
传输安全：版本检查与更新包下载全程走HTTPS（内网部署采用内部CA证书），符合等保三级要求；
完整性校验：下载完成后客户端校验SHA-256哈希，不一致则删除文件并提示重新下载；
来源可信：更新包由发布流水线用平台私钥生成RSA数字签名，客户端内置公钥验签，防止更新包被篡改或植入恶意程序；
接口鉴权：版本检查与管理接口复用一期统一身份认证与权限体系，管理端仅限平台管理员；
降级保护：签名/哈希校验失败、强制更新未完成时，客户端不允许静默继续运行旧版本（强制更新场景）。
七、发布流程与灰度策略
构建：发布流水线产出更新包，自动计算SHA-256并签名，上传至更新包存储；
登记：在版本管理后台创建版本记录，填写更新说明，初始状态为草稿；
灰度：先对内部测试租户/5%用户发布，观察升级成功率与崩溃上报；
放量：无异常后按30%→100%逐步扩大灰度范围；
兜底：灰度期间发现严重问题，一键下线版本，客户端按钮自动消失；已升级用户不受影响。
八、异常场景与处理
异常场景
处理策略
版本检查接口超时/失败
静默失败，不影响使用，下一个轮询周期重试；连续失败期间按钮不渲染
下载中断（断网）
自动重试3次，支持Range断点续传；最终失败按钮进入失败态，用户可手动重试
磁盘空间不足
下载前检查剩余空间（更新包大小×2），不足时Tooltip提示并阻止下载
哈希/签名校验失败
删除更新包，按钮进入失败态，上报服务端告警（可能为篡改或存储损坏）
安装失败
回滚至旧版本（安装包自带回滚或重新运行旧版本安装包），上报失败日志
服务端版本下线
下次检查时hasUpdate返回false，客户端隐藏按钮并清理已下载更新包
